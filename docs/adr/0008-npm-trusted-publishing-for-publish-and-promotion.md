# npm publication and promotion authenticate through trusted publishing

The release workflow authenticates both `npm publish` and the `npm dist-tag add` promotion through npm trusted publishing. npm exchanges the publish job's GitHub OIDC token for a short-lived publish token, and no npm token is stored in the repository. The engine stays credential-agnostic. It spawns npm with the inherited environment, and the calling workflow owns authentication, so Internal and Fuse configure their own workflows without an engine change. npm 11.21.0 added OIDC authentication for `dist-tag` ([npm/cli#10038](https://github.com/npm/cli/pull/10038)), which removed the limitation [ADR 0004](0004-pack-and-verify-is-the-consumer-seam.md) left open.

**Consequences**: the publish job needs npm 11.21.0 or later on `PATH`, and the npm bundled with `.node-version` is older, so the workflow installs an exact npm before the engine runs. For a `workflow_call`, npm validates the calling workflow's filename, so the package needs a trusted-publisher entry for `merge.yml` and a separate entry for `publish-release.yml` when a manual retry runs. Each entry names the `npm` environment and allows both publish and dist-tag. A retry publishes without provenance, because npm signs provenance for `GITHUB_SHA` and a retry dispatch runs at main's head rather than the recorded archive's commit. An adapter that strips credentials must do so only around its own child processes, because the engine's npm calls need the OIDC request variables after `pack` returns.

**Considered options**: keeping the npm token, rejected because every workflow run can read it and it can publish from anywhere until it expires; npm staged publishing, rejected because it needs a human 2FA approval for every version, which breaks publish-on-merge; publishing straight to the channel tag, rejected because it drops the `pending` staging the engine verifies before promotion.
